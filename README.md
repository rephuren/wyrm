## Зачем это

Фаззинг — один из немногих способов находить баги памяти (переполнения, выходы за границы, деление на ноль, UB), которые статический анализ и ручной ревью пропускают. `wyrm` — учебная реализация идеи AFL: не претендует на производительность настоящего AFL++/libFuzzer, но показывает всю механику изнутри — инструментацию покрытия, мутации, обратную связь по рёбрам графа потока управления, минимизацию крашей.

## Как это работает

1. **Инструментация.** Цели собираются с `-fsanitize-coverage=trace-pc-guard`: компилятор вставляет вызов на каждом переходе между базовыми блоками. Среда выполнения (`coverage_rt.cpp`) при каждом вызове отмечает байт в карте покрытия — общей памяти между фаззером и целью.
2. **Мутации.** Побитовые/побайтовые флипы, арифметика, «интересные» граничные константы (-1, 0, 128, MAX_INT...), вставка/удаление кусков, сращивание двух входов из корпуса — набор в духе havoc-режима AFL.
3. **Обратная связь.** После каждого запуска фаззер проверяет, появились ли новые ненулевые байты в карте покрытия. Если да — вход достиг кода, которого раньше не видели, и остаётся в корпусе.
4. **Обнаружение крашей.** Цели собраны с ASan и UBSan. Падение (SIGSEGV/SIGABRT, код выхода санитайзера) сохраняется в `crashes/` вместе с текстом отчёта.
5. **Минимизация.** Delta-debugging (бинарный разрез входа) плюс побайтовое обнуление сводят краш-инпут к минимальному воспроизводимому PoC.

Каждый запуск цели — отдельный процесс (`fork`+`exec`), с таймаутом и перехватом stderr. Это проще и надёжнее persistent-режима, хотя и медленнее: учебная реализация выбирает понятность над скоростью.

## Учебные цели

В `targets/` три маленькие программы с намеренными багами — полигон, чтобы показать, что фаззер реально находит:

| цель | баг |
| :-- | :-- |
| `parse_header` | переполнение буфера: длина поля не проверяется против размера `name[64]` |
| `vuln_buffer` | три бага за байтом-переключателем: переполнение стека, деление на ноль, выход за границы массива |
| `json_lite` | неограниченная рекурсия в разборе вложенности — переполнение стека на глубоком вводе |

Это учебные программы, а не уязвимости чужого ПО. Баги в них оставлены специально: не используй эти цели вне полигона и не запускай их на машине с важными данными.

## Запуск

```bash
make targets           # собрать учебные цели (clang++, ASan+UBSan+coverage)
make                    # собрать сам wyrm
make test               # 19 модульных и сквозных тестов (включая реальный фаззинг целей)

build/wyrm fuzz --target build/target_vuln_buffer --corpus corpus --seed-dir corpus_seeds/vuln_buffer --max-runs 200000
build/wyrm replay --target build/target_vuln_buffer --input crashes/crash-1.bin
build/wyrm minimize --target build/target_vuln_buffer --input crashes/crash-1.bin --output min.bin
```

## Реальный прогон

Настоящий вывод `wyrm fuzz` на `target_vuln_buffer` с затравками только для двух из трёх багов (переполнение и выход за границы; деление на ноль намеренно не засеяно):

```
запусков: 4000   покрытие: 280 рёбер   корпус: 9 входов   крашей: 30   скорость: 107/с
  ▓ crashes/crash-1.bin  — targets/vuln_buffer.cpp:15:36: index 16 out of bounds for type 'char[16]'
  ▓ crashes/crash-3.bin  — targets/vuln_buffer.cpp:31:18: index 903218 out of bounds for type 'int[4]'
  ...
```

Любопытный и честный результат: третий баг, деление на ноль, за эти 4000 запусков не нашёлся, хотя его затравка была в корпусе. Ему нужно попадание байта ровно в значение 42 — слепые битфлипы и арифметика с шагом ±35 такое почти не угадывают. Зато выход за границы массива (`int[4]`, баг с которым фаззер вообще не был засеян явно) мутатор нашёл сам, просто дрейфуя по первому байту-переключателю. Это ровно тот случай, для которого в разделе «Дальше» заявлен CMPLOG: сравнение с точной константой — слабое место havoc-мутаций без знания о сравнениях в коде цели.

Минимизация одного из найденных крашей: `7 → 6 байт`, итог `52 00 00 00 00 ff` — то есть один байт `'R'` и мусор, задающий индекс вне диапазона.

## Как проверялось

- 19 тестов: мутатор (детерминизм по сиду, границы размера, splice), корпус (сохранение/восстановление с диска), карта покрытия, минимизатор на синтетическом предикате.
- Сквозные тесты реально компилируют и фаззят три учебные цели как подпроцессы и проверяют, что баги находятся: переполнение в `parse_header`, минимум 2 из 3 багов в `vuln_buffer` за ограниченный бюджет запусков, минимизация реального краша до компактного PoC.
- При первом прогоне 2 из 19 тестов падали не из-за логики фаззера, а из-за настройки целей: на этой связке Apple clang 21 (arm64) `-O1` не всегда расставляет redzone вокруг стековых буферов, и переполнение проходило мимо ASan — помогло только `-O0`. Отдельно UBSan по умолчанию печатает диагностику и **продолжает выполнение** вместо падения — нужен `-fno-sanitize-recover=all`. Проверил оба случая отдельным минимальным репро, прежде чем менять флаги.
- На Apple Silicon (arm64, Apple clang 21) полный прогон тестов занимает несколько минут — узкое место в `fork`+`exec` на процесс, это ожидаемо при такой архитектуре и написано сознательно, не доработка «на будущее поверх уже готового».

## Ограничения

- **Производительность.** Процесс на запуск — в сотни раз медленнее persistent-режима AFL (переиспользование процесса через `fork()` после инициализации). На простых целях это пара тысяч запусков в секунду, а не сотни тысяч.
- **Только один воркер.** Параллельный фаззинг (несколько процессов на общем корпусе) не реализован.
- **Карта покрытия 64 КБ без разрешения коллизий** — как у классического AFL, на крупных целях возможны редкие совпадения хэшей рёбер.
- **Нет планировщика по энергии/приоритету** входов: выбор из корпуса равномерно случайный, а не по «интересности» входа.
